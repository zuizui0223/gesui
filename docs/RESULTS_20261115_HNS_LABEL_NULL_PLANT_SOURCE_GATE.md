## B. 植物N指数への同一流域接続 — 元資料検査を先行

植物群集NUTRIの構築には、同一の454 H7×期間について
1. 元のPlantae speciesKeyごとの記録数/出現種を取得・整合検査する。
2. 原出版Tichý et al. (2023) 欧州EIV NUTRIの受理種を名称照合・別辞書の種IDとの照合を行う。原本はZenodo v2配布、最新版や類似名での恣意的置換は不可。
3. original GBIF記録50件以上、NUTRIスコア付き種10種以上、形質照合率40%以上という仕様の前に、まず植物種記録の上限機会を確認する。
4. 最低100 H7×期間/40独立H6/5国の支持上限を下回る場合は本格モデルに進まない。
5. 主指標は種均等NUTRI平均、副次はGBIF記録重み付き平均。*植物被度・葉N・植食・送粉・実際のN投入量を表すものではない*。

新設した `analysis/20261115_plant_trait_source_gate/source_gate.py` は元のrun #43593227162の真正JSON（SHA256 `251f8514684fe8ea62d94ddc8c6eeefb59976471d84d7389b682aff6637144e4`）と、454行の本来パネルのみを使用して、記録数・speciesKey数・原本のspeciesKey網羅率を監査する**源資料のみ**のコードである。**EIV種名照合/植物N指数/Wとの相関は実行していない**。GitHub Actionsで源資料ゲートが検証されたら、結果に応じた次段階を決める。

PR #12の36地点植物NUTRI監査では原本指標のマッチ率が処理場側で15/18組低く、元の18組のうち正式判定条件を満たすのは9組のみだった。従って単に「数値NUTRIがある種に絞った」植物群集を真の植生群集とみなしてはいけない。
